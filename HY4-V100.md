# Hy4-flash on 4× V100: the fast14 recipe

This guide serves [tencent/Hy4-flash](https://huggingface.co/tencent/Hy4-flash) on four V100-SXM2-32GB GPUs with
this engine and the `fast14` launch profile. The weights are leoncca's
[Hy4-flash-AWQ-g32](https://huggingface.co/leoncca/Hy4-flash-AWQ-g32), unchanged. At load time the engine converts the
dense layers to int8 and reads the shared expert from a calibrated int8 cache that you build once (step 4).

Model page with the measurements: https://philtompkins.com/models/hy4-flash

## 1. Hardware and software

- 4× V100-SXM2-32GB on NVLink, tensor parallel 4. Our cards ran at their 300 W limit.
- Host RAM for the Engram tables, which stay in pinned host memory: about 60 GiB in total across the four ranks.
- Disk: 167.3 GB for the checkpoint.
- CUDA 12.8 (CUDA 13 dropped Volta), Python 3.12, torch 2.10.0+cu128, gcc 14. We used NVIDIA driver 580.

## 2. Download the weights

```bash
hf download leoncca/Hy4-flash-AWQ-g32 \
  --revision 6a6ab55577a64d74426696f78a847491b5a127d6 --local-dir hy4-flash-awq-g32
```

Our measured copy matches this revision's `SHA256SUMS` file byte for byte. Later revisions of the repo change only the
README.

Download to the directory you will serve from. The shared-expert cache is keyed by the checkpoint's file sizes,
modification times and safetensors headers, so copying the checkpoint somewhere else afterwards means rebuilding the
cache.

## 3. Build the engine

There is no prebuilt wheel. Build from the tag:

```bash
git clone --branch hy4-fast14-20261124 https://github.com/philbert440/hy4-flash-v100
cd hy4-flash-v100
uv venv --python 3.12 .venv
export CUDA_HOME=/usr/local/cuda-12.8 PATH=/usr/local/cuda-12.8/bin:$PATH
export CC=gcc-14 CXX=g++-14 NVCC_CCBIN=g++-14 CUDAHOSTCXX=g++-14
export TORCH_CUDA_ARCH_LIST=7.0 CMAKE_CUDA_ARCHITECTURES=70 FLASH_ATTN_V100_CUDA_ARCH_LIST=7.0
export VLLM_TARGET_DEVICE=cuda MAX_JOBS=16 NVCC_THREADS=1
uv pip install --python .venv/bin/python -e . --torch-backend=cu128
```

The build compiles the three Hy4 extensions (`_sm70_hy4_moe_C`, `_sm70_hy4_attn_C`, `_sm70_hy4_next_C`) with the rest of
the engine. We built from a local mirror of the CMake dependencies. This command fetches the same dependencies from the
network, and we have not run it on a clean machine.

## 4. Build the shared-expert cache

The fast profiles store the shared expert as int8 with group size 32 and GPTQ error compensation. The packs come from a
short calibration run on the four GPUs, which took 158 seconds including startup for us:

```bash
.venv/bin/python tools/hy4/shared_w8_cache.py calibrate \
  --model hy4-flash-awq-g32 --calib calib.jsonl --out w8-cache
```

- `calib.jsonl` holds your calibration text, one `{"text": "..."}` per line. The tool takes 24 documents of at least 128
  tokens, cut to 640 tokens each. Our cache used 15,119 tokens of agent transcripts and chat that we can't publish, so
  a cache built from other text will differ slightly.
- The tool runs the model with the int8 paths off (profile `fast2`) and records each shared-expert projection's input
  statistics. It writes `w8-cache/<checkpoint key>/<build key>/` with four rank files of about 154 MB each and a
  manifest with their SHA-256 values. The server checks those hashes at startup.
- The build key covers `w8.py`, `w8_cache.py`, `profile.py` and the Hy4 extension binaries. If you rebuild the
  extensions or change those files, the server refuses the old cache. When the quantizer and the checkpoint are
  unchanged, rebind the existing packs instead of calibrating again:

  ```bash
  .venv/bin/python tools/hy4/shared_w8_cache.py rebind \
    --model hy4-flash-awq-g32 --cache w8-cache/<checkpoint key>/<old build key> --out w8-cache
  ```

## 5. Serve

```bash
export CUDA_DEVICE_ORDER=PCI_BUS_ID CUDA_VISIBLE_DEVICES=0,1,2,3   # one NVLink quad
export VLLM_HY4_PROFILE=fast14
export HY4_W8_SHARED_GPTQ_CACHE=$PWD/w8-cache/<checkpoint key>/<build key>
export VLLM_WORKER_MULTIPROC_METHOD=spawn VLLM_USE_V2_MODEL_RUNNER=0
export VLLM_SM70_QUANT_BACKEND=turbomind VLLM_USE_BREAKABLE_CUDAGRAPH=0
export PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True
export CUDA_HOME=/usr/local/cuda-12.8 NVCC_CCBIN=g++-14

.venv/bin/vllm serve hy4-flash-awq-g32 --served-model-name hy4-flash \
  --tensor-parallel-size 4 --decode-context-parallel-size 1 \
  --dtype half --kv-cache-dtype fp8_ds_mla \
  --max-model-len 262144 --max-num-batched-tokens 2048 --max-num-seqs 4 \
  --gpu-memory-utilization 0.97 \
  --enable-chunked-prefill --no-disable-hybrid-kv-cache-manager --enable-prefix-caching \
  --enable-prompt-tokens-details \
  --reasoning-parser hy_v4 --enable-auto-tool-choice --tool-call-parser hy_v4 \
  --speculative-config '{"num_speculative_tokens":5,"method":"dfly"}' \
  --compilation-config '{"mode":0}' --no-async-scheduling
```

- This runs the built-in DFly2 drafter. For plain decode, drop `--speculative-config` and `--no-async-scheduling`, and
  use `--compilation-config '{"mode":0,"cudagraph_mode":"FULL_DECODE_ONLY"}'`.
- At startup the log prints `Hy4 profile=fast14 active=[...]` with every speed path it turned on. Any switch you set in
  the environment overrides the profile.
- KV cache: 657,298 tokens plain and 529,491 tokens with the drafter, at these settings.
- `--max-num-batched-tokens 2048` is the prefill chunk. In a test on the pre-fix version of the same prefill reader,
  8192 cut the 32K time to first token by about 17% and left 26% fewer KV tokens.
- Our benchmark servers ran without `--enable-auto-tool-choice --tool-call-parser hy_v4`. Without them, a request with
  `tools` gets HTTP 400. The parser is ReVolta's. With a tool schema in the prompt, an earlier build of this
  engine (`fast8`) gave well-formed tool calls on 12 of 12 requests. We did not test the parser itself.
- We pinned the server to the GPUs' NUMA node with `numactl --cpunodebind=<node> --preferred=<node>`.
- Thinking is on by default. Set `chat_template_kwargs: {"reasoning_effort": "no_think"}` per request to turn it off.

## 6. Check it

```bash
curl -s localhost:8000/v1/chat/completions -H 'Content-Type: application/json' -d '{
  "model": "hy4-flash", "max_tokens": 64,
  "messages": [{"role": "user", "content": "Name the capital of France."}],
  "chat_template_kwargs": {"reasoning_effort": "no_think"}}'
```

## What fast14 measured

One request unless stated. Rates count tokens after the first streamed token.

| | `reference` profile | `fast14` |
|---|---:|---:|
| Plain decode, short context | 31.0 tok/s | 106.7 tok/s |
| Plain decode, four requests (total) | 96.2 tok/s | 301.5 tok/s |
| DFly2 drafter, 96 real prompts | | 137.7–139.3 tok/s |
| Decode step at 128K context | | 12.0 ms (was 20.1 on `fast10`) |
| Time to first token, 32K prompt | | 12.6 s (was 38.1 on `fast11`) |

`reference` is this engine with every speed path off. The short-context plain rows were measured on `fast7` in an
independent verification. Every later profile matched them within noise. The model page lists the conditions, the
panels and the quality checks for each number.
