# Hy4-flash on 4× V100: the fast14 recipe

This guide serves [tencent/Hy4-flash](https://huggingface.co/tencent/Hy4-flash) on four V100-SXM2-32GB GPUs with
this engine and the `fast14` launch profile. The default weights are our
[Hy4-flash-W4A16-AWQ](https://huggingface.co/philbert440/Hy4-flash-W4A16-AWQ): leoncca's
[Hy4-flash-AWQ-g32](https://huggingface.co/leoncca/Hy4-flash-AWQ-g32) layout with the routed experts fitted again and
the Engram tables re-encoded, about half the KL distance to BF16 at the same plain decode speed. It ships the
shared expert's int8 packs inside the checkpoint, so nothing else needs downloading or building. At load time the
engine converts the dense layers to int8 and reads those packs (step 4).

leoncca's checkpoint, unchanged, still works with the same engine and a separate shared-expert cache (step 4, second
part). [Which checkpoint](#which-checkpoint) compares the two.

Model page with the measurements: https://philtompkins.com/models/hy4-flash

## 1. Hardware and software

- 4× V100-SXM2-32GB on NVLink, tensor parallel 4. Our cards ran at their 300 W limit.
- Host RAM for the Engram tables, which stay in pinned host memory: about 60 GiB in total across the four ranks.
- Disk: 168.5 GB for our checkpoint (167.3 GB for leoncca's).
- CUDA 12.8 (CUDA 13 dropped Volta), Python 3.12, torch 2.10.0+cu128, gcc 14. We used NVIDIA driver 580.

## 2. Download the weights

```bash
hf download philbert440/Hy4-flash-W4A16-AWQ --local-dir Hy4-flash-W4A16-AWQ
(cd Hy4-flash-W4A16-AWQ && sha256sum -c SHA256SUMS)
```

The model card lists the method, calibration data, quality checks and licence.

For leoncca's checkpoint instead:

```bash
hf download leoncca/Hy4-flash-AWQ-g32 \
  --revision 6a6ab55577a64d74426696f78a847491b5a127d6 --local-dir hy4-flash-awq-g32
```

Our measured copy matches this revision's `SHA256SUMS` file byte for byte. Later revisions of the repo change only the
README. Its shared-expert cache is keyed to the checkpoint directory (step 4), so download it to the directory you
will serve from. If you move or copy that checkpoint later, run `shared_w8_cache.py rebind` again.

## 3. Install the engine

Install the prebuilt SM70 wheel from the
[`hy4-fast14-20261125` release](https://github.com/philbert440/hy4-flash-v100/releases/tag/hy4-fast14-20261125):

```bash
TAG=hy4-fast14-20261125
WHEEL=1cat_vllm-1.5.4.dev157+hy4fast14.20261125-cp312-cp312-linux_x86_64.whl
gh release download $TAG -R philbert440/hy4-flash-v100 -p "$WHEEL" -p SHA256SUMS -p shared_w8_cache.py
sha256sum -c --ignore-missing SHA256SUMS
uv venv --python 3.12 .venv
uv pip install --python .venv/bin/python "./$WHEEL" ninja --torch-backend=cu128
```

Without the GitHub CLI, download the same files from the release page. The wheel is for Python 3.12, torch
2.10.0+cu128 and V100 (SM70) only. It was built from tag `hy4-fast14-20261125` with CUDA 12.8.1 and gcc 14 on Ubuntu
24.04 (glibc 2.39), and it includes the three Hy4 extensions (`_sm70_hy4_moe_C`, `_sm70_hy4_attn_C`,
`_sm70_hy4_next_C`). Some kernels compile on first start, so the CUDA 12.8 toolkit, a C++ compiler and `ninja` are
still needed at runtime.

To build from source instead:

```bash
git clone --branch hy4-fast14-20261125 https://github.com/philbert440/hy4-flash-v100
cd hy4-flash-v100
uv venv --python 3.12 .venv
export CUDA_HOME=/usr/local/cuda-12.8 PATH=/usr/local/cuda-12.8/bin:$PATH
export CC=gcc-14 CXX=g++-14 NVCC_CCBIN=g++-14 CUDAHOSTCXX=g++-14
export TORCH_CUDA_ARCH_LIST=7.0 CMAKE_CUDA_ARCHITECTURES=70 FLASH_ATTN_V100_CUDA_ARCH_LIST=7.0
export VLLM_TARGET_DEVICE=cuda MAX_JOBS=16 NVCC_THREADS=1
uv pip install --python .venv/bin/python -e . --torch-backend=cu128
```

The source build fetches its CMake dependencies from the network. The release wheel was built this way in a clean
container. The cache tool is `tools/hy4/shared_w8_cache.py` in the clone.

Release `hy4-fast14-20261125` is the first with the sidecar loader (`HY4_W8_SHARED_SIDECAR`). The earlier release
`hy4-fast14-20261124b` serves our checkpoint only through its `shared-w8-cache/` folder and `rebind`, as in the
model card.

## 4. The shared expert's int8 packs

The fast profiles store the shared expert as int8 with group size 32 and GPTQ error compensation. The packs are made
offline.

### Our checkpoint: the sidecar (default)

Our checkpoint ships the packs in `hy4-v100-shared-w8.safetensors`. Set `HY4_W8_SHARED_SIDECAR=1` and leave
`HY4_W8_SHARED_GPTQ_CACHE` unset (step 5). At load time the engine checks that the sidecar was made for this
checkpoint's files (names, sizes, safetensors headers and JSON files, not modification times), slices each rank's
part and lays it out with no rounding. The model index does not list the sidecar, so other loaders ignore it. There is
nothing else to download, build or rebind.

With the switch on and no sidecar in the checkpoint, the engine falls back to `HY4_W8_SHARED_GPTQ_CACHE`.

### leoncca's checkpoint: the cache

For leoncca's checkpoint the packs come from a cache: four rank files of 154 MB each and a `manifest.json` with their
SHA-256 values. The server checks those hashes at startup. Choose one of two paths.

The cache directory is named `<checkpoint key>/<build key>`. The checkpoint key covers the checkpoint's file names,
sizes, modification times and safetensors headers, and the JSON files. The build key covers `w8.py`, `w8_cache.py`,
`profile.py` and the Hy4 extension binaries. Your download and your install always differ from ours in modification
times and binaries, so both paths end with a directory keyed to your files.

#### Path A: download our cache (recommended)

This is the cache all our measurements used. It was calibrated on 15,119 tokens of agent transcripts and chat. The
calibration text is not published. The manifest records only token counts and SHA-256 values of the token ids.

```bash
gh release download $TAG -R philbert440/hy4-flash-v100 -D hy4-w8-download \
  -p manifest.json -p 'rank-*.pt' -p SHA256SUMS
(cd hy4-w8-download && sha256sum -c --ignore-missing SHA256SUMS)
.venv/bin/python shared_w8_cache.py rebind \
  --model hy4-flash-awq-g32 --cache hy4-w8-download --out w8-cache
```

`rebind` checks that your checkpoint has the same content as ours (file names, sizes, safetensors headers and JSON
files, not modification times) and that each rank file matches its SHA-256 value. It then writes
`w8-cache/<checkpoint key>/<build key>/` with links to the downloaded rank files, and prints that path. Keep
`hy4-w8-download` in place. If the checkpoint differs, `rebind` stops and you need path B.

#### Path B: calibrate your own cache

```bash
.venv/bin/python shared_w8_cache.py calibrate \
  --model hy4-flash-awq-g32 --calib calib.jsonl --out w8-cache
```

- `calib.jsonl` holds your calibration text, one `{"text": "..."}` per line. The tool takes 24 documents of at least
  128 tokens, cut to 640 tokens each, so documents of 640 tokens or more use the full budget. Pick text like your
  traffic.
- It runs the model on the four GPUs with the int8 paths off (profile `fast2`), records each shared-expert
  projection's input statistics, quantizes with GPTQ, and prints the cache path. Set `CUDA_VISIBLE_DEVICES` and the
  other environment variables from section 5 first. It took 159 seconds on our machine, including startup.
- A cache from other text differs slightly from ours. We tested a cache built from paragraphs of the public
  WikiText-103 test split (24 documents, 9,152 tokens). About 7% of its bytes differ from our cache. It decoded at the
  same speed, and on our 2,560-position quality check against an FP32 forward of the checkpoint its distance did not
  differ measurably from our cache's: KL +0.0001 nats (95% CI −0.0029 to +0.0031) and top-1 agreement −0.31 points
  (−0.94 to +0.23).

After you rebuild the extensions or change the files in the build key, run `rebind` on your existing cache directory
instead of calibrating again.

To turn a cache into a sidecar inside a checkpoint whose shared-expert weights match the calibration checkpoint, use
`tools/hy4/qpack_shared_sidecar.py make --model CKPT --cache CACHE --cache-model CALIB_CKPT`. It checks the result
byte for byte against the cache. Write it after every JSON file and safetensors shard in `CKPT` is final, because the
sidecar binds to their content.

## 5. Serve

```bash
export CUDA_DEVICE_ORDER=PCI_BUS_ID CUDA_VISIBLE_DEVICES=0,1,2,3   # one NVLink quad
export VLLM_HY4_PROFILE=fast14
export HY4_W8_SHARED_SIDECAR=1   # read the packs from our checkpoint
# leoncca's checkpoint instead: unset HY4_W8_SHARED_SIDECAR and set
# HY4_W8_SHARED_GPTQ_CACHE=$PWD/w8-cache/<checkpoint key>/<build key>   (the path rebind or calibrate printed)
export VLLM_HY4_DFLY_GRAPHS=both   # CUDA graphs for the drafter; every DFly2 number used this
export VLLM_WORKER_MULTIPROC_METHOD=spawn VLLM_USE_V2_MODEL_RUNNER=0
export VLLM_SM70_QUANT_BACKEND=turbomind VLLM_USE_BREAKABLE_CUDAGRAPH=0
export PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True
export CUDA_HOME=/usr/local/cuda-12.8 NVCC_CCBIN=g++-14

.venv/bin/vllm serve Hy4-flash-W4A16-AWQ --served-model-name hy4-flash \
  --tensor-parallel-size 4 --decode-context-parallel-size 1 \
  --dtype half --kv-cache-dtype fp8_ds_mla \
  --max-model-len 262144 --max-num-batched-tokens 2048 --max-num-seqs 4 \
  --gpu-memory-utilization 0.97 \
  --enable-chunked-prefill --no-disable-hybrid-kv-cache-manager --enable-prefix-caching \
  --enable-prompt-tokens-details \
  --reasoning-parser hy_v4 --enable-auto-tool-choice --tool-call-parser hy_v4 \
  --speculative-config '{"num_speculative_tokens":5,"method":"dfly"}' \
  --compilation-config '{"mode":0}' --no-async-scheduling
```

- This runs the built-in DFly2 drafter. For plain decode, drop `--speculative-config` and `--no-async-scheduling`, and
  use `--compilation-config '{"mode":0,"cudagraph_mode":"FULL_DECODE_ONLY"}'`. `VLLM_HY4_DFLY_GRAPHS` only affects
  the drafter.
- At startup the log prints `Hy4 profile=fast14 active=[...]` with every speed path it turned on. Any switch you set in
  the environment overrides the profile.
- KV cache: 657,298 tokens plain and 529,491 tokens with the drafter, at these settings.
- `--max-num-batched-tokens 2048` is the prefill chunk. In a test on the pre-fix version of the same prefill reader,
  8192 cut the 32K time to first token by about 17% and left 26% fewer KV tokens.
- Tool calls use ReVolta's `hy_v4` parser. Without `--enable-auto-tool-choice --tool-call-parser hy_v4`, a request
  with `tools` gets HTTP 400. With `tool_choice: "auto"` (the default) we checked 8 cases with six OpenAI-style tool
  schemas (single calls, two parallel calls, nested objects, arrays, a shell command with quotes, no tool needed, and
  a tool result fed back), with thinking on and off, streaming and not, on the plain and DFly2 layouts. Every call
  came back well-formed: valid JSON arguments that match the schema, unique ids, `finish_reason: "tool_calls"`, and no
  tool markup in the content. Streaming and non-streaming returned the same calls. `tool_choice: "required"` and a
  named function are not enforced: the parser turns off guided decoding for them, because guided JSON would break the
  model's own tool-call format. The model decides whether to call a tool. Our benchmark servers ran without the parser
  flags; they do not change decode speed.
- We pinned the server to the GPUs' NUMA node with `numactl --cpunodebind=<node> --preferred=<node>`.
- Thinking is on by default. Set `chat_template_kwargs: {"reasoning_effort": "no_think"}` per request to turn it off.

## 6. Check it

```bash
curl -s localhost:8000/v1/chat/completions -H 'Content-Type: application/json' -d '{
  "model": "hy4-flash", "max_tokens": 64,
  "messages": [{"role": "user", "content": "Name the capital of France."}],
  "chat_template_kwargs": {"reasoning_effort": "no_think"}}'
```

## What fast14 measured

One request unless stated. Rates count tokens after the first streamed token.

| | `reference` profile | `fast14` |
|---|---:|---:|
| Plain decode, short context | 31.0 tok/s | 106.7 tok/s |
| Plain decode, four requests (total) | 96.2 tok/s | 301.5 tok/s |
| DFly2 drafter, 96 real prompts | | 137.7–139.3 tok/s |
| Decode step at 128K context | | 12.0 ms (was 20.1 on `fast10`) |
| Time to first token, 32K prompt | | 12.6 s (was 38.1 on `fast11`) |

`reference` is this engine with every speed path off. The short-context plain rows were measured on `fast7` in an
independent verification, with leoncca's checkpoint. Every later profile matched them within noise. The model page
lists the conditions, the panels and the quality checks for each number.

## Which checkpoint

Both checkpoints have the same layout and run on the same engine at `fast14`. Quality is KL(candidate ‖ BF16) in nats
and top-1 agreement with Tencent's BF16 checkpoint over 2,560 teacher-forced positions (40 held-out prompts × 64
positions). Brackets are paired bootstrap 95% intervals.

| | leoncca | ours | ours − leoncca [95% CI] |
|---|---:|---:|---:|
| Offline FP32 forward: mean KL | 0.0849 | 0.0409 | −0.0440 [−0.0598, −0.0306] |
| Offline FP32 forward: top-1 | 92.58% | 95.16% | +2.58 pp [+1.64, +3.48] |
| This engine, 1 stream: mean KL | 0.0930 | 0.0454 | −0.0476 [−0.0631, −0.0342] |
| This engine, 1 stream: top-1 | 91.95% | 94.45% | +2.50 pp [+1.45, +3.55] |
| Plain decode, seeded, 1 stream | 107.07–108.10 tok/s | 107.03–108.09 tok/s | within noise |
| Plain decode, seeded, 4 streams | 307.05–307.42 tok/s | 307.33–307.72 tok/s | within noise |
| DFly2, 496 prompts: accepted tokens per verify | 1.942 | 1.890 | −0.052 [−0.094, −0.011] |
| DFly2, 496 prompts: tok/s after the first token | 150.2 | 148.0 | −2.15 [−4.01, −0.30] (−1.4%) |

The trade-off: the built-in DFly2 drafter was trained on the original model's outputs, and it accepts slightly fewer
of our checkpoint's tokens, so speculative decoding is about 1.4% slower. On identical context the acceptance is
nearly the same; most of the loss comes from the different text our checkpoint generates, mainly on agent and chat
prompts with thinking off. Plain decode speed is unchanged. Choose leoncca's checkpoint if that 1.4% matters more to
you than the quality gain.
